# תוכנת WMS בעברית — תכנון וארכיטקטורה

**המטרה:** לבנות מערכת ניהול מחסן/מלאי **עברית-תחילה** (Hebrew-first) שתשתווה ותעלה על
[תוכנת *נשר* של תבל (Tevelsoft)](https://tevelsoft.co.il/nesher-pro.asp), תוך שימוש חוזר
במערכת הקיימת **CarbonWMS** (Next.js 16 + Postgres + אפליקציית Flutter למסופון + RFID),
במקום להתחיל מאפס.

> סטטוס: **תכנון בלבד** — אין בשלב זה שינויי קוד באפליקציה.

---

## 1. רקע: מהי נשר

נשר היא תוכנת ניהול המוסכים הנפוצה ביותר בישראל (כ‑1,500 התקנות). היא עברית‑מקורית, RTL,
ועוטפת ליבת ניהול מלאי במודולים עסקיים. המודולים הרלוונטיים
([מקור](https://tevelsoft.co.il/nesher-pro.asp),
[מדריך מחסנים PDF](http://tevelsoft.co.il/Updates/%D7%A0%D7%99%D7%94%D7%95%D7%9C%20%D7%9E%D7%97%D7%A1%D7%A0%D7%99%D7%9D%20-%20%D7%A0%D7%A9%D7%A8.pdf)):

- **מלאי רב‑מחסני** — ריבוי מחסנים, כולל *רכבי שירות* כמלאי נייד; מלאי כולל מאוחד לכל פריט.
- **שריון/הזמנות** — שריון חלקים לרכבים/עבודות שמתוכננים לעתיד.
- **ספירות לכל מחסן** — ספירות מלאי נפרדות לכל מחסן שמתגלגלות למלאי הכולל.
- **העברות בין מחסנים** — העברת מלאי בין מחסנים, עם דוח העברות.
- **ניפוק לכרטיס עבודה** — בעת ניפוק חלק לעבודה יש לציין את מחסן המקור.
- **שכבה עסקית** — הצעות מחיר, מחירונים (כולל מחירוני יבואן), הזמנות ספקים, חו"ז (לקוחות/ספקים),
  הוצאות, הפקת חשבוניות, CRM/לקוחות, שעות עובדים, ניהול מסמכי רכב.
- **דוחות** — דוח ערך מלאי, רשימת העברות, ספירות לכל מחסן ועוד.

**חולשות של נשר שנוכל לנצח:** חוויית שולחן‑עבודה ישנה (Windows), אין RFID, מובייל חלש,
אינטגרציות סגורות. **היתרונות שלנו:** ספירת **RFID מובנית**, ממשק **ווב מודרני + מסופון**,
**אינטגרציות פתוחות** (Lightspeed, Shopify), **סנכרון בזמן אמת**.

## 2. מה כבר קיים (CarbonWMS — לעשות שימוש חוזר, לא לבנות מחדש)

המאגר הוא מערכת WMS בוגרת ב‑Next.js. מיפוי המשטחים הרלוונטיים:

| תחום | היום | שימוש חוזר ליעד "נשר" |
|------|------|----------------------|
| מעטפת/ניווט | `components/layout/Sidebar.tsx`, `components/wms-shell-client.tsx` | תרגום + RTL |
| מלאי | `app/(main)/inventory/*` — קטלוג, קטגוריות, מיקומי אחסון, ספירות, העברות, ייבוא | ליבה; להוסיף רב‑מחסני + שריון |
| מיקומים | `app/(main)/settings/locations`, `LocationSwitcher` | הופך ל"מחסנים" (כולל סוג רכב/נייד) |
| ספירות | `inventory/cycle-counts`, `reports/count-sessions` | ספירות לכל מחסן כבר ממודלות |
| העברות | `inventory/transfers/{in,out}`, `reports/transfers/*` | העברות בין מחסנים כבר קיימות |
| RFID/מסופון | `app/(main)/rfid/*`, `mobile/carbon_wms` (Flutter) | יתרון מול נשר |
| אינטגרציות | Lightspeed, Shopify (`app/(main)/integrations/*`) | יתרון |
| נתונים | `scripts/schema.sql` + `scripts/migrations/*` (Postgres) | להרחיב במיגרציות חדשות |
| ערכת נושא | `lib/theme-boot.ts` + `components/theme/theme-provider.tsx` | **תבנית לחיקוי עבור i18n** |

**מצב התרגום הנוכחי:** אין. `<html lang="en">`, תוויות אנגלית מקובעות, ללא תלות i18n.
זהו הפער המשמעותי ביותר אל מול "תוכנה בעברית".

## 4. ארכיטקטורה

### 4.1 תשתית לוקליזציה / RTL (שלב 1 — ליבת ה"עברית")

לחקות את מערכת **ערכת הנושא** הקיימת (סקריפט אתחול + provider), כך שהשפה תוחל לפני
הציור הראשון — ללא הבהוב וללא אי‑התאמת hydration.

```
lib/i18n/
  dictionary.ts      # טיפוס Locale, DEFAULT_LOCALE="he", dirForLocale(), translate()
                     # מיפוי מחרוזת-מקור-אנגלית -> עברית (תוספתי: t("Inventory") -> "מלאי")
  locale-boot.ts     # WMS_LOCALE_BOOT_SCRIPT: קובע <html lang/dir> מ-localStorage לפני ציור
components/i18n/
  locale-provider.tsx# "use client" LocaleProvider + useLocale()/useT(), נשמר ל-localStorage
```

חיווט:
- `app/layout.tsx` → `<html lang="he" dir="rtl">` + הזרקת `WMS_LOCALE_BOOT_SCRIPT` ל‑`<head>`
  (ליד `WMS_THEME_BOOT_SCRIPT`).
- `components/wms-shell-client.tsx` → לעטוף את המעטפת ב‑`<LocaleProvider>`; להוסיף מתג שפה.
- רכיבים מתרגמים על‑ידי עטיפת תוויות האנגלית הקיימות: `t("Inventory")`. **מפתוח לפי מחרוזת
  המקור האנגלית** כך שאף מבנה נתונים של רכיב אינו משתנה, והאנגלית נשארת ברירת המחדל (fallback).

**אסטרטגיית RTL (Tailwind v4):** להשתמש בכלי עזר *לוגיים* במקום *פיזיים*, כך שבסיס קוד אחד
משרת את שני הכיוונים:
- `border-r` → `border-e`, `left-0` → `start-0`, `-right-1` → `-end-1`.
- מגירה מחוץ למסך: `${visible ? "translate-x-0" : "-translate-x-full rtl:translate-x-full"}`
  (מחליקה אל צד ה‑*start* בשני הכיוונים).
- לבדוק מחלקות כיווניות‑פיזיות בכל המאגר
  (`grep -rE '\b(left|right|pl-|pr-|ml-|mr-|translate-x)'`) ולהמיר את המשמעותיות ללוגיות.

**סדר התרגום** (נראוּת גבוהה תחילה): מעטפת/ניווט → לוח בקרה → מלאי → ספירות → העברות →
דוחות → הגדרות → מסופון (Flutter `intl`/`.arb`).

### 4.2 הרחבות מודל נתונים (Postgres, מיגרציות תוספתיות)

מיגרציות חדשות תחת `scripts/migrations/` (לעולם לא לערוך את בסיס `schema.sql`):

- `warehouses` — `id, code, name_he, name_en, type('fixed'|'vehicle'), is_active`.
  להעלות מיקומים קיימים או למפות מיקומים→מחסנים.
- `stock_by_warehouse` — `(warehouse_id, sku) -> qty`; מלאי כולל = SUM על כל המחסנים.
- `reservations` — `id, sku, warehouse_id, qty, job_id?, reserved_for, expires_at, status`.
- `work_orders` + `work_order_lines` — ניפוק לעבודה; כל שורה מציינת `warehouse_id` מקור.
- שלב 4+: `suppliers`, `purchase_orders`, `price_lists`, `quotes`.

לשמור על מיגרציות אידמפוטנטיות (`IF NOT EXISTS`, `ALTER` שמור) לפי מוסכמות המאגר; לכבד
`WMS_AUTO_MIGRATE`.

### 4.3 קצה / מובייל

- מסופון Flutter (`mobile/carbon_wms`) מקבל עברית באמצעות `intl` + `Directionality` ל‑RTL;
  שימוש חוזר באותם מפתחות תרגום היכן שניתן.
- ספירת RFID מזינה **ספירות לכל מחסן** — היתרון הבולט מול הזרימה הידנית של נשר.

## 5. מפת דרכים בשלבים

| שלב | תוצר | היקף |
|-----|------|------|
| **1. עברית + RTL** | האפליקציה עברית‑תחילה, ניתנת להחלפה, RTL תקין | תשתית i18n + תרגום מעטפת/ניווט/לוח בקרה; ביקורת פריסה |
| **2. מחסנים** | רב‑מחסני כולל רכבים; מלאי כולל מאוחד | מודל `warehouses`/`stock_by_warehouse`; מיקומים→מחסנים; ספירות לפי מחסן |
| **3. עבודות + שריון** | כרטיסי עבודה, ניפוק לעבודה, שריון | מודול חדש + מנוע שריון |
| **4. רכש** | ספקים, הזמנות רכש, מחירונים, הצעות מחיר | מודולים עסקיים חדשים |
| **5. כספים** | חו"ז, חשבוניות, הוצאות | בנייה או אינטגרציה לחשבונאות |

כל שלב ניתן לשחרור עצמאי. שלב 1 לבדו מספק את המיצוב "חלופה עברית לנשר"; שלבים 2–3 משיגים
שוויון פונקציונלי לליבת המחסן; 4–5 סוגרים את פער החבילה העסקית.

## 6. סיכונים והחלטות לאישור

- **גישת i18n:** מילון פנימי קל‑משקל (מוצע — אפס תלויות, fallback לאנגלית, מחקה את מערכת
  ערכת הנושא) **מול** `next-intl` (שפות מבוססות‑ניתוב, יותר תקורה). מומלץ הגישה הקלה לשלב 1;
  לשקול מחדש אם נדרשות שפות מבוססות‑URL או כללי ריבוי (plural).
- **מיקומים מול מחסנים:** להחליט אם להרחיב את מודל המיקומים הקיים או להציג טבלת `warehouses`
  נפרדת (מומלץ: טבלה חדשה, ולמפות מיקומים אליה).
- **היקף הכספים:** לבנות חשבוניות/חשבונאות באופן מקורי (גדול) מול אינטגרציה לספק חשבונאות
  ישראלי (מומלץ) — משפיע על כל שלב 5.
- **שלמות התרגום:** שלב 1 משחרר מעטפת/ניווט; תרגום מלא של כל המשטחים הוא הדרגתי. מחרוזות
  המקור האנגליות נשארות כ‑fallback מובטח כך ששום דבר אינו נשבר באמצע ההטמעה.
