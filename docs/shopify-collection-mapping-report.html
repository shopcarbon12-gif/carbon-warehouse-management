0 · The one-paragraph version

This page is a merchandising control panel for a Shopify store's navigation menu. On the left it shows the store's menu tree (MEN ▸ CLOTHING ▸ JEANS …), each menu item linked to a Shopify collection. On the right it shows the store's products, one row per UPC, and for each product it automatically decides which collections it should belong to by reading the Carbon SKU (gender + season + category digit) and looking the answer up in a hard-coded rules "workbook." A human reviews/approves those decisions, then clicks Commit / Push, and the app writes the membership changes back into Shopify (adds/removes the product to/from collections). Everything it shows is pulled live from the Shopify Admin GraphQL API; the only thing it stores in its own Postgres database is the menu-tree structure, the node→collection map, and each user's in-progress "draft" decisions plus audit logs.

1 · What this page actually is

Carbon-gen is the Carbon Creative Studio — a workspace app with several tools (image generator, SEO, Instagram widget, etc.). Collection Mapping is one of those tools, promoted to its own top-level URL. Its job is to keep the Shopify storefront's category navigation correct:

  • Collections in Shopify are groups of products (e.g. "Men's Jeans"). They can be manual (you add products by hand) or automated (Shopify auto-fills them from rules). This tool primarily manages the manual membership — which products sit in which collection.
  • The menu / navigation tree is the storefront's dropdown menu. Each menu item points at a collection. This tool lets you edit that tree (add/rename/move/delete items, up to ~4 levels) and sync it to Shopify.
  • The bridge between them is the mapping: "menu node X corresponds to collection Y," and "product P should be in collections [Y1, Y2…]." The page computes the second part automatically from the product's SKU.

So a merchandiser opens the page, the app says "here are 6,000 products and here's where each one should go," the merchandiser approves, and the app makes Shopify match.

Implementation footprint: ~22,000 lines. The UI is one giant client component (components/shopify-collection-mapping.tsx, 11,834 lines, of which ~4,500 are a single CSS block) plus a drag-and-drop tree (components/shopify-menu-items-tree.tsx, 2,228 lines). The backend is one fat route (app/api/shopify/collection-mapping/route.ts, 4,458 lines) plus a data repository (1,519 lines), a rules engine (529), an auto-mapper (204), and a KPI/classifier (282).

Key insight: Shopify is the source of truth for products, collections, and the menu. One row per UPC (products with the same barcode are collapsed together). First/prev/next/last, "Page X of Y", and a per-page selector (20/50/100/200/500).

An entirely separate "Idea 3" experience: a KPI pill strip, a card list (one card per product with thumbnail, expand, suggestions), bottom-sheets for the menu and suggestions, an image lightbox, and a sticky bottom dock with the commit menu + pager. Same data and actions, phone-friendly chrome.

5 · The work loop (load → push)

1
Load. On open (and whenever you search/sort/page/filter), the browser does one GET /api/collection-mapping. The server pulls all collections + all products from Shopify, syncs the live menu into its DB, auto-maps every product, paginates, and merges in your saved drafts.
2
Auto-decide. For each product row the server has already computed: the collections the rules say it belongs to (Auto Path), a Decision (Auto-mapped / Suggested / Manual review), and any conflicts. Suggestions deliberately outrank a clean auto-map so nothing is silently changed without a human glance.
3
Review. You filter by "Needs Review," click suggestion chips to accept/reject, optionally tweak the menu tree, mark rows "Approved," or "Hold from Sync." Every click autosaves to your personal draft (debounced 550 ms) — so you can leave and come back.
4
Preview. "COMMIT CHANGES → Push selected/all" opens a preview that lists exactly which products get added to / removed from which collections, and which rows are skipped (and why: not reviewed, missing data, on hold, no change).
5
Push. Confirm runs the push: per eligible row, the server reads the product's current collections, computes the minimal add/remove diff (with "ancestor closure" so parent collections are included), and calls Shopify collectionAddProducts / collectionRemoveProducts. Progress shows in a local job tracker.
6
Sync & settle. Committed rows are marked, the page reloads from Shopify, and rows that now match their target flip to Synced. Their drafts auto-clear.

6 · The auto-mapping brain

This is the cleverest part and the most Carbon-specific. It turns a SKU into a set of collections.

Step 1 — Parse the SKU

Carbon SKUs encode a route (gender + season) and a category digit. The parser yields a routeKey — 11 Men-Summer, 12 Men-Winter, 21 Women-Summer, 22 Women-Winter — plus a digit 0–9 for the category.

Step 2 — Look it up in the "workbook"

There is a hard-coded table (a transcription of a spreadsheet) where each route + digit maps to one or more targets: a menu path (MEN > CLOTHING > JEANS), a direct collection (COLLECTION: jeans-men), or an intentional ERROR. Some rows are exact (route+digit is enough); others are ambiguous and need the product's text (title/type/SKU) to disambiguate.

Step 3 — Resolve

  • Exact rows win. If a clean route+digit rule exists, use it.
  • Ambiguous rows are scored by how many of the rule's category keywords appear in the product text; highest score (then best coverage) wins. Ties are broken by per-bucket keyword tables (e.g. distinguishing LEGGINGS vs SWEATPANTS vs PANTS), and if still tied it gives up and asks for human review.
  • Conditional targets (IF JOGGER: …) only apply if that keyword is present.

Step 4 — Decide & explain

The decision is Suggested (something to approve), Auto-mapped (clean, no follow-ups), or Manual review (couldn't resolve). When it can't decide, it records a precise reason (PARSE_FAILED, MISSING_ROUTE_KEY, MULTIPLE_MATCHES, LEGACY_REVIEW_REQUIRED for old "C…" SKUs, etc.) and a human sentence shown in the explainer modal. It also runs conflict detection (e.g. a UPC whose gender contradicts the assigned path) and surfaces a one-click fix.

Why this matters for the port: the entire rules workbook is Carbon's own SKU scheme. It's pure, hard-coded logic with no external dependency — it ports verbatim. The only question is whether you feed it Shopify product SKUs (as today) or CarbonWMS catalog SKUs (see the plan).

7 · The menu tree

The left panel is a live editor for the Shopify storefront menu. Notable details:

  • Shopify allows 3 levels of menu nesting; the app allows 4. Level-4 nodes are kept only in the app's database (keys prefixed local4:) and are never pushed to Shopify, so the storefront stays valid.
  • Editing any node (add/rename/move/delete/visibility) re-pushes the entire menu to Shopify via one menuUpdate mutation — last-write-wins, no locking (a real-world risk with two editors).
  • There's a hard-coded "mega-menu seed" (~99 nodes: MEN / WOMEN / JEANS / REWARDS / BECOME AFFILIATE) that can rebuild the whole menu from scratch.
  • The node↔collection mapping lives in the DB; the menu structure is reconciled from Shopify on each load (new live nodes are upserted, stale ones removed, but local-4 and disabled nodes are preserved).

8 · Statuses & KPIs

Every product row is classified into exactly one workflow status, and the KPI tiles just count them:

StatusMeaning (plain English)
Push FailedThe last push to Shopify for this row errored.
SyncedWhat's in Shopify already matches the target, and any required human review is done.
Ready to PushDecisions are made/approved but Shopify hasn't been updated yet (add-pending or removal-pending).
Needs ReviewA human still needs to look — manual-review decision, a conflict, manual edits, or an unapproved suggestion.

Other computed metrics: a collection audit (total collections, mapped vs unmapped, duplicates) and a push plan summary (eligible vs skipped rows, total additions/removals). All computed in the browser from the loaded page of data.

9 · The backend & Shopify calls

One fat route handles everything. The browser only ever calls /api/collection-mapping, which is a thin alias of /api/shopify/collection-mapping (there's also a Pages-Router compat bridge). Two HTTP methods:

  • GET — the big page load (collections + products + menu + auto-map + your drafts).
  • POST — everything else, multiplexed by a body.action string (15 actions): rename collection, save/clear drafts, get/download logs, refresh/save/restore menu, save mappings, set node mapping, add/edit/move/delete menu node, and the big one — toggle-nodes / bulk-toggle-nodes which adds/removes products to/from collections in Shopify.

How Shopify is talked to

Everything is GraphQL against https://{shop}/admin/api/2025-01/graphql.json with the header X-Shopify-Access-Token: <token>. No REST. The client retries on throttling (HTTP 429 or GraphQL THROTTLED) with exponential backoff. Reads are cached in-process (collections 60s, products 45s). GraphQL operations used: read collections, products, menus, pages/blogs, product.collections; write menuUpdate, collectionAddProducts, collectionRemoveProducts, collectionUpdate.

How the token is found

Per request: figure out the shop (request param → SHOPIFY_SHOP_DOMAIN → most-recently-installed shop in the DB), then find a working admin token — first a per-shop token stored in the shopify_tokens Postgres table (written by the OAuth callback), else an env token (SHOPIFY_ADMIN_TOKEN_<SHOP> or the global SHOPIFY_ADMIN_ACCESS_TOKEN). Each candidate is probed; the first that works (and ideally has navigation scope) is cached 60s. No token → 401 "Shop not connected."

10 · The database (5 tables)

Plain Postgres, one shared instance, multi-tenant by a shop text column on every table (no per-tenant schema). There are no migration files — the tables are created in code on first use (CREATE TABLE IF NOT EXISTS). If no DB is configured, the whole thing falls back to in-memory maps.

11 · Credentials & config (the 3rd-party part)

The only third party is Shopify (plus the app's own Postgres). Two ways to authenticate, and the code supports both at once:

OAuth mode (per-store, preferred)

SHOPIFY_REDIRECT_URI

The OAuth callback stores the token in shopify_tokens. Good for multiple stores.

Static-token mode (single store, simplest)

SHOPIFY_ADMIN_ACCESS_TOKEN
Admin API token (custom app)
SHOPIFY_SHOP_DOMAIN
the *.myshopify.com store

No OAuth needed. The token must carry product + online-store-navigation scopes.

Always needed: a Postgres connection string (COOLIFY_DATABASE_URL / POSTGRES_URL / DATABASE_URL). Optional: SHOPIFY_API_VERSION (defaults to 2025-01), SHOPIFY_COLLECTION_MAPPING_MENU_HANDLE (defaults to main-menu). The page also respects two kill-switches: DISABLE_SHOPIFY_COLLECTION_MAPPING (hides the page) and, on Coolify, SHOPIFY_LIVE_UPDATES_ON_COOLIFY (must be true or every write is blocked with 503).

12 · Auth, gating & kill-switches

  • Login gate. Carbon-gen's middleware (the fork uses proxy.ts, not middleware.ts) requires a carbon_gen_auth_v1 cookie; unauthenticated users are bounced to /login. A "meta-review" role is locked out entirely. In dev, AUTH_BYPASS=true auto-logs-in a super-admin.
  • The legacy URL /studio/shopify-collection-mapping is 308-redirected to the canonical /shopify-collection-mapping.
  • No in-route RBAC. The API only reads the session to tag your drafts; protection is entirely the cookie gate + the Coolify write kill-switch. Any logged-in user can drive collection writes.
  • The Coolify write block (proxy.ts) returns 503 for all non-GET /api/shopify/* unless SHOPIFY_LIVE_UPDATES_ON_COOLIFY=true — a deliberate production safety valve.

13 · Quirks & risks worth knowing

  • Whole-menu rewrites, last-write-wins. Two people editing the tree can clobber each other.
  • Synchronous pushes. A big "push all" runs inside one 120-second request — no queue. Large batches can time out.
  • In-memory caches per process. Fine on a single instance; multiple instances can show slightly stale collections/products for up to 45–60s.
  • No SSL config on the DB pool — relies on the network/connection string.
  • Tables auto-created in code, no migrations — replicating the schema means copying the CREATE TABLE block verbatim.
  • The whole feature is one 11.8k-line component — hard to partially adopt; it's effectively all-or-nothing.

PLAN · Copy it into CarbonWMS under the Categories page

Goal: rebuild this exact tool inside CarbonWMS, reachable from the Categories page. Below is the honest mapping of what transfers cleanly, what has to change, the credentials needed, and a step-by-step sequence. This is a plan for discussion — there's one big product decision to make first.

Decision #1 (please read first): what data does it operate on?

This tool is fundamentally a Shopify tool — it maps Shopify products into Shopify collections and edits the Shopify storefront menu. CarbonWMS, by contrast, is a Lightspeed-based warehouse system; it actually removed its old Shopify integration (migration 009_remove_shopify.sql). So "copy as is" means WMS gains a Shopify control panel that talks to your Shopify store — independent of WMS's Lightspeed catalog. The alternative is to adapt it to map your WMS catalog (matrices/custom_skus) into the WMS Categories you just built. These are very different projects. My recommendation: port as-is first (it's a faithful copy and the SKU rules already match Carbon), then decide separately whether to also wire it to WMS catalog data. The rest of this plan assumes as-is.

P6 · Effort & risk, honestly

  • Largest risk & effort: the 11.8k-line UI component — it's monolithic and assumes its own endpoint shape. Porting it is mostly mechanical but voluminous.
  • Medium: the API route re-wiring (DB + session + proxy allowlist) and the migration.
  • Low: the pure rule/auto-map libs and the Shopify client.
  • Watch-outs: WMS's proxy allowlist (new /api/* paths 401 until added); the live-write kill-switch; the per-process cache if WMS runs multiple instances; and the fact that this writes to your live Shopify store — keep writes flagged off until verified.
